---
description: Plan the test cases behind this change, wait for your approval, run them, and report pass or fail
argument-hint: "[base-branch]"
allowed-tools: Bash(node:*), Bash(git diff:*), Bash(git log:*), Bash(uv sync:*), Bash(npx playwright install:*), Bash(npm install:*), Read, Glob, Grep, Write, Edit, Agent
---

Check the current change with QAMaster's gate. You approve what runs before anything runs. Follow the `Gate` skill. The CLI is `node "${CLAUDE_PLUGIN_ROOT}/src/cli/main.mts"`, run from the app repo.

1. Run `node "${CLAUDE_PLUGIN_ROOT}/src/cli/main.mts" plan`, adding `--base $ARGUMENTS` if an argument was given, and `--preset fast|standard|full` if the person asked for one (otherwise `gate.preset` decides, `standard` by default). Its first line names the base branch, and its `Selection:` line names the preset, the selectors and the model that picks groups. Exit 3 means a plan is waiting for approval.
2. If the `Selection:` line says `groups picked by …` and the plan lists **Other groups**, pick groups. (A `fast` or `full` preset, `QAMASTER_AI=off`, CI and the pre-push hook never pick groups, and then the line has no `groups picked by`.) Run `git diff <base>...HEAD`, then choose which listed groups the change could affect:
   - if the line names a model (`sonnet`, `opus`, `haiku`, `fable`), start a subagent with the Agent tool and pass that name as its `model`; give it the diff and the **Other groups** list and ask for each group the change could affect, with a one-line reason tied to the diff;
   - if it says `the session's model`, make the choice yourself.
   Then run the plan again with `--tag '<group>=<reason>'`, one `--tag` per group, keeping the same `--preset`. Use only group names from the list; never invent one, and never take a group a subagent names that isn't in the list.
3. **Automate (Q39).** If the QA project has no automation folder, say so, and say that the plan will run 0 cases until there is one: point the person to `… app create` and then `… automate <plan-id>`, and offer to run them (ask first; never skip silently). If it has an automation folder, run `… automate <plan-id>`. If it lists cases to **draft** or **update**, write their scripts with the `AutomationCode` skill, run `… check-scripts` until it passes, then offer a trial run: `… automate <plan-id> --try` runs the new scripts once against the running app and records nothing (it needs the app up and the test account set; ask first, as it drives a browser). Show its failures with their kind (assertion failed, step couldn't act on the page, script error); fix script errors and step failures, and say what an assertion failure means (the app or the case, not the script). A trial pass does not make a script proven. Then run `… automate <plan-id> --done`. It prints the plan again, now with the drafted cases in it. Say which scripts are new or changed, and that they're uncommitted.
4. Show the final plan exactly as printed, in a code block, and note its plan ID. Say which groups you added and why. If the plan prints a `warning:` that no selected case covers or visits the changed code, repeat it in your own words before asking for approval. Point out **Not run** (manual or BROKEN), **Shared files** and **Coverage gaps**.
5. Ask: **"Do you approve plan `<id>`?"** The person can approve it as is, add test cases or groups ("add TC5103", "add the cart group"), remove some ("drop TC4410"), or stop. **Then end your turn and wait.** Approving the plan also approves the scripts drafted for it. Never approve on their behalf. Only their reply to this question counts.
6. After their yes, run `… approve <plan-id> --yes` with `--add …` and `--remove …` for their edits (comma-separated IDs like `TC5103`, or group names). `--yes` is needed because you have no terminal to ask on (D10); pass it only after their reply to the question in step 5. If approval is refused because it would run 0 test cases (the plan matched cases that can't run, or every item was removed), show the message and ask the person what to do; pass `--allow-empty` only if they say in their own words to run none. If they said stop, say nothing ran and end.
7. Run `… run <plan-id>` and show the verdict exactly as printed.
8. Summarise in one or two sentences: pass or fail, and for each failure the test case and the first line of its error (the verdict reason already names it). Name each flaky case on its own line (it still counts as a pass, with a warning). Say that only the app's own origin (`baseURL`) is watched for 5xx and page errors: an API on another origin is not watched, so a pass does not show the API is healthy. If it passed, say `git push` is now allowed for this commit. A failure marked "new script failed" may be the script's fault or the app's: say so.

`--yes` means one thing on each command, so keep them apart: on `approve` it is the person's yes to the plan shown (needed with no terminal); on `check` it plans, approves and runs in one go, which only a person's own terminal command does, so never use `check --yes` for them; `--allow-empty` on either approves a plan that runs 0 cases, and only the person's explicit words allow it.

Exit codes: 0 pass, 1 fail, 2 blocked, 3 awaiting approval. On 2, show the message and its fix, and stop. If it says HEAD moved, offer to plan again. A blocked run can be the machine's setup, not the code (Q41): the test environment isn't set up (`uv sync`), Playwright's browser isn't installed (`npx playwright install chromium`, or `uv run playwright install chromium`), its system libraries are missing (`sudo npx playwright install-deps chromium`, which the person runs themselves), the automation folder needs `npm install`, or the app isn't running. Show the message as printed, say what the command downloads, ask whether to run it, and run it only after an explicit yes. Never install in the background, and never run `sudo`.

When you hand the person a command to run in their own terminal, give one they can paste: every value (run name, plan id, path) filled in, never a `<placeholder>`, and the launcher by its absolute path, `node <absolute path of the QA project>/.qamaster/bin/qam.mjs <command>` (the launcher exists only in the QA project, written by `qam setup`). If `qam doctor` shows `WARN launcher`, hand over the plugin path instead and suggest running setup again from the plugin. This command runs from the app repo, which has no launcher: always name the QA project.
