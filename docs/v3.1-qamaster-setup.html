What works today

Shipped App discovery

Scan the app's code, crawl the running app with a robot browser that can't change data, and build the screen map (DSM). 0.3.2 fixed a change-password form being taken for a sign-in page, and folds ULID IDs into :id.

Shipped Test design and publish

Claude writes test cases grounded in the screen map and app knowledge, a validator checks them, a person reviews them, and publish sends them to a local CSV store by default, or to Azure DevOps Test Plans. Publishing again changes nothing that hasn't changed.

Shipped The change gate

For each code change: a plan of the cases it touches, scripts drafted just in time for cases that have none, a person's approval, a run on pytest or playwright-bdd, and a verdict with evidence. A push from Claude Code waits for it.

Shipped Status and checks

/qamaster:status shows every stage with its evidence and the next step. qam doctor checks the store, the runners, the browser and the app URL, and says how to fix each.

Shipped Install from a zip

scripts/package.sh builds a zip for Claude desktop and one for the Claude CLI, and checks both. install.md says how to load each.

Setup, step by step

Each step's choice defaults to what ships today. Pick another to see where it's planned; the two boxes after the steps follow your picks.

  1. Install, and pick your entry points

    Tick every tool you work in. Each tick sets QAMaster up inside that tool: it writes the tool's own rules or steering file, a hook where the tool has one (the same push check Claude Code runs), and later its MCP registration, all in your working copy of the app repo. Every file it creates is kept out of commits, and qam integrations remove takes it all back out. Ticking Kiro, for example, creates .kiro/steering/qamaster.md and .kiro/hooks/qamaster.json and lists both in .git/info/exclude.

    Q3 one CLI behind every surface · Q27 every install recorded · Q29 entry points are a checklist · Q43 each tool gets its own files, hooks included, kept out of commits

    Later here: each tool's files and the git pre-push hook for any terminal or IDE v1.1, PR checks v1.1, MCP registration through the QAMaster MCP server v2, an IDE extension Later.

  2. Set up the QA project, and run doctor

    Setup asks two things, in order: where the app's code is, then where its working copy lives on this machine. It then links the QA project (the folder you run it in, or --repo) to that code and the app's URL, and qam doctor checks every prerequisite. A missing tool blocks with the command to fix it, and nothing is downloaded without a yes.

    Q26 a local folder or git URL, validated, and a clone goes where you choose · Q28 the host decides which PR checks fit · Q30 read through the host's API · Q41 setup problems block, no downloads without a yes

    Next here: when no folder is given, setup asks with three suggestions: this folder, the folder you've used most before, or a path you type (Q47, built in 0.4.0) Accepted, not built. Later: reading the code through the GitHub or Azure Repos API, with no clone v1.1; Bitbucket, GitLab and other servers Later.

  3. Choose the test case store

    Where reviewed cases live. Local by default: a CSV in the QA project, kept in git, with no account or network needed. Choose Azure DevOps when the team is ready (QAMASTER_STORE=ado); a project that has already published keeps its store. Once published, the store is the source of truth, and a local cache keeps reads fast.

    Q6 the store is the source of truth · Q23 a replaceable adapter · Q34 the file store and the cache · Q36 the file store's JSON form · Q44 local first

    Later here: a project spreadsheet, then Jira through Xray or Zephyr Later.

  4. Map the app (DSM)

    Scan the code's routes, crawl the running app (signed in if needed), and build the screen map that test design and the gate both use. Every write request is blocked during the crawl.

    Q15 read-only toward the app · 0.3.2 T1 sign-in detection · T2 ULID IDs

    Next here: faster crawls and a time estimate before running (S1–S7), forms without a <form> tag 0.3.3. Later: locators from the crawl, API discovery v2; Appium Later.

    Claude Code skills that describe the app (its screens, flows and words), built from the screen map and kept in step with it.

  7. Design and review the test cases

    Claude drafts cases with hallucination tolerance 0: every step points at evidence. A validator checks them, and a person approves the run before anything is published.

  8. Publish

    A dry run first; --apply writes, and only after a yes. Tags are derived from facts, a script link is added only once the script is pushed, and nothing is ever deleted.

    Publishes to

  9. Check each change: plan, automate, approve, run, verdict

    The gate picks the cases a change needs and says why, drafts scripts just in time for cases that have none, waits for approval, runs each case on the runner its link names, and records a verdict with evidence. Its local files stay out of the app's commits.

  10. Hold the push until the gate passes

    In Claude Code, a push waits for a passing verdict on the current commit. Repos QAMaster has never planned in are never blocked.

    Self-contained HTML reports fed by the gate, and feedback that proposes new or stale cases, broken links and defect drafts for a person to act on. Not built: qam report blocks today.

      Use it now

      You need Node.js 24 and git, a web app with a reachable test instance, and its code in git. Azure DevOps credentials are needed only for the ADO store. Install from a zip (install.md) or from a checkout:

      # In Claude Code, from a checkout of this repo
claude --plugin-dir ./plugin

# Then, in the QA project
/qamaster:status                      # every stage, its evidence, and the next step
qam setup --app <AppName> --url <test-app-url> --source <app-folder-or-git-url>
qam doctor                            # what's missing, and how to fix it
/qamaster:check                       # before a push: plan, scripts, approval, run, verdict

      Review cases before publishing, and approve a plan before tests run. Never crawl or run tests against production unless that's been explicitly reviewed and approved.
