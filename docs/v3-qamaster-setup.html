Roadmap, not released

QAMaster v3 setup

A planning view of the product capabilities listed for v3: reuse existing automation, trace changes and tests, explain failures, measure value, and strengthen secret handling.

Version status: The current plugin is 0.3.1. Product v3 is a future scope in the product plan, not a released plugin or an approved implementation schedule. Its setup steps and capabilities below are therefore a target, not commands you can enable today.

What works today

Available Web app discovery

Scan an app repository, crawl a reachable web app with Playwright, and build a DSM. Crawl safety blocks data-changing requests by default.

Available Test design and publishing

Generate evidence-grounded test cases for review, then publish to Azure DevOps Test Plans or the local file store.

Available Automation and gate

Generate Playwright-BDD scripts and run them, or run an existing pytest suite. The change gate creates an approved plan and records a verdict.

Planned v3 capabilities

  1. Work with existing automation frameworks Planned

    Detect and analyze a team's current framework and generate into it where supported. Today, Playwright-BDD is the generated framework; pytest is supported as a runner for existing tests. Cypress, Cucumber-JVM and SpecFlow generation are not currently shipped.

  2. Impact and traceability matrices Planned

    Extend today's code-to-screen DSM impact and test selection with broader impact and traceability views linking changes, requirements, screens, cases and automation.

  3. Root-cause evidence Planned

    Use commits and logs as evidence to help explain test failures. Failure evidence and gate verdicts exist today; the planned v3 work is the root-cause analysis layer.

  4. Value metrics Planned

    Measure tokens, time and effort saved. QAMaster does not currently provide these product metrics.

  5. Secrets vault and security scan Planned

    Add an encrypted secrets vault and security scanning. Today, credentials are supplied through environment variables or ignored local .env files; there is no QAMaster vault.

  6. Visio MCP server Planned

    Add Visio as a context source through an MCP server. The QAMaster MCP server and context-source integration are also not in the current 0.3.1 release.

Use the current plugin

For a real setup now, use a web application with a reachable test instance and source code in Git. Node.js 24 and Git are required. Choose Azure DevOps Test Plans or the local file store; ADO credentials are needed only for ADO operations.

# Load the plugin in Claude Code for this session
claude --plugin-dir /path/to/QAMaster/plugin

# Or use the CLI to set up a QA project
qam setup --app <AppName> --url <test-app-url> --source <app-folder-or-git-url>
qam doctor

Review generated test cases before publishing, and approve a gate plan before tests run. Do not use production for crawl or test runs unless the action has been explicitly reviewed and approved.

What must be decided before calling this a v3 setup

Framework boundary

Which existing frameworks are detected, analyzed, and supported for generation—and which are runner-only?

Traceability model

Which identifiers and evidence connect code changes, requirements, screens, test cases, and runs?

Security model

How vault encryption, access, rotation, scanning, and secret redaction should work.

Evidence and metrics

Which sources can support root-cause explanations and how effort or value is measured without overstating precision.
