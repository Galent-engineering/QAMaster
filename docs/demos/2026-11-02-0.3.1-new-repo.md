# QAMaster: full-loop walkthrough on a new repository (0.3.1)

The first walkthrough of the whole loop, on an application no demo has used. It goes from an empty QA folder to a pushed change that the gate checked:
- set up the project, map the app (DSM), and write and review test cases;
- publish them;
- change the app's code;
- let `/qamaster:check` pick the cases, draft their scripts, run them after your approval, and gate the push.

## Part 0. Prerequisites (from the clean Docker run)

QAMaster now checks and explains each of these. The point is to see whether its messages are enough, so don't install anything ahead of time unless you already have it.

| Needed for | What | Check |
|---|---|---|
| Everything | Node.js 24 or later, npm, git 2.20+, `git config user.email` | `node --version`, `git --version` |
| Crawling the app (DSM) | Playwright and Chromium in the QA project | `qam setup` installs them; on Linux also `sudo npx playwright install-deps chromium` |
| Running the drafted scripts | `npm install` in the automation folder | `qam check-scripts` says so if it's missing |
| pytest tests, if the app has any | uv (or python3 with pytest) and `uv sync` in the test folder | `qam doctor` → `runner pytest` |
| The app itself | Running and reachable at its URL | `qam doctor` → `app URL` |

## Part A. Set up and map the app

| Step | Do | Expected |
|---|---|---|
| A1. App | Clone the app (a full clone, not shallow) and start it locally. Note its URL | The app opens in a browser |
| A2. Install | In the new QA folder: `git init`, `claude plugin marketplace add ~/claude-plugins/qamaster --scope project`, `claude plugin install qamaster@qamaster-local --scope project`, `claude plugin list` | qamaster 0.3.1, enabled, project scope |
| A3. Setup | *"Set up QAMaster for `<App>`. It runs at `<URL>` and its code is in `<app repo>`."* | Config written. The app name is what you said, not the folder's name. Playwright installed |
| A4. Doctor | *"Run QAMaster doctor."* (`qam doctor`) | Every line ok or WARN. Each FIX says what to do |
| A5. Sign-in (if the app has one) | Create `.env.dsm` with a test account yourself. Claude never reads it | doctor or the crawl uses it; `.env.dsm` stays git-ignored |
| A6. DSM | `/qamaster:dsm` | Routes found in code and screens crawled. Write down the counts and anything missing |
| A7. App knowledge | *"Build the AUT skills for this app."* | Skills under `.claude/skills/AUT_<App>*`, with citations into the code |

> **Feedback, Part A** (A1–A7: counts, surprises, anything the DSM got wrong)

## Part B. Test cases: generate, review, publish

| Step | Do | Expected |
|---|---|---|
| B1. TestGen | *"Write test cases for the `<module>` module."* Pick a module with a form and a sign-in-free flow | It validates with 0 findings and is rendered. No passwords in titles or steps (0.2.2) |
| B2. Review | Read the run, then answer the question it asks: **"Do you approve run X as reviewed?"** Also try saying *"show the dry run"* first | Only your yes to that question records the review. "Show the dry run" doesn't |
| B3. Publish dry run | `/qamaster:publish` with `QAMASTER_STORE=file` | The preview shows creates, `path:` tags (a shallow folder is `dir/*`), smoke counted across the plan, and "Scripts not pushed" if there are any |
| B4. Apply | Say yes | The cases land in `testcases/testcases.csv`. Commit the QA project (`git add -A && git commit`) |

| Step | Do | Expected |
|---|---|---|
| C1. Create | *"Create the automation folder."* (`qam app create`) | `<App>/` from the playwright-bdd template, with `app.json` holding your URL |

## Part D. A code change, gated

| Step | Do | Expected |
|---|---|---|
| D1. Gate the app repo | In the app repo: `.env` with `QAMASTER_TEST_ROOT=<QA project>` and `QAMASTER_STORE=file`; then *"Add the Claude Code entry point for QAMaster here"* (`qam integrations add claude-code`) | The integration is recorded. The app repo's `git status` doesn't list `.env` or `.qamaster/plans` (0.3.1 F7) |
| D2. A change | On a branch in the app repo, change a source file behind the module you published, and commit | A normal commit |
| D3. Push without a check | Ask Claude to push | **Blocked** by the hook: "Run /qamaster:check first" |
| D4. Check | `/qamaster:check` | A plan with the cases the change touches (covers / smoke / visits), the cases that stay manual, and any coverage gaps. Then the automate step: Claude drafts scripts for the selected cases, runs `check-scripts`, records them, and asks **"Do you approve plan X?"** |
| D5. Look before you approve | Read the drafted scripts in `<App>/` | Selectors sit in `src/web/locators/`, and credentials come from environment variables. Cases that need an account or a CAPTCHA may stay manual, with the reason given |
| D6. Approve | Say yes | It runs. A new script that fails says "new script failed: check the script or the app". A missing browser or an app that isn't running is **blocked** with the fix, not failed |
| D7. Push | Ask Claude to push again | Allowed when the verdict passed |
| D8. Commit the scripts | In the QA project: review, commit and push the drafted scripts | Yours to do. QAMaster never commits |
| D9. Publish the links | `/qamaster:publish`, then apply | The cases get `bdd:@TC-…` links and a `Script:` line pinned to the commit |
| D10. Check again | Make another small change in the app repo, then `/qamaster:check` | The published scripts run from the store's links, kept as they are. Nothing needs drafting |

> **Feedback, Part D** (which cases it picked, and were they the right ones? the drafted scripts' quality, the time it took, the messages)
>
