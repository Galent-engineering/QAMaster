## Step 4. Apply
> Result: ✅ waited / ❌ smoke
> **Did it wait?** Yes. Nothing was written until I said "Yes, apply". It created the project, the plan, 4 suites and 243 cases, with 0 held back.
> **Did it do exactly what I said?** Not for smoke. The 4 previews promised 11 + 15 + 2 + 10 = **38** smoke cases, and Claude reported "the default smoke suggestions were applied". ADO actually has **20**: AccountAuth 11, CommerceOrders 9, CatalogEngagement 0, ChallengesWeb3 0.
> - **Cause:** `smoke.max` (20) applies to the whole plan (`suggestSmoke` subtracts the smoke already in the store). All 4 previews ran before the project existed, so each one counted 0 in the store. The runs were then applied one after another, so the cap was hit partway through the second run.
> - **Result:** the preview and the apply disagreed without any warning, and the summary repeated the preview instead of the apply output.
> - Unticking a smoke case (`--skip-smoke`) was not tested.

The `testcases.json` files and `.qamaster/ledger.json` had the same checksums before and after, so nothing was written. The header also says who reviewed the run ("Reviewed by … on 2026-10-30"), which is a nice touch.

## Step 6. Hand edit becomes a conflict
> Result: in progress (part 1 done).
> **Part 1, edit in the store:** in ADO I added a step to TC-SCOREBOARD-001 (ADO #239): "TestForHashChnage" / "Cache for qa master detect changes in test case". ADO also saved an empty 4th step. The revision went from 1 to 2.
> A live dry run (`--refresh`) of all 4 runs still said `Unchanged` and `Nothing to publish.`, with exit 0. This is by design. Publish only compares with the store when the *run's* version of a case has changed (its hash differs from the ledger). A store-only edit is never overwritten, and it's never flagged either.
> ⚠️ **No sign the store has drifted:** the dry run fetched revision 2 but didn't say that #239 had been edited in ADO since it was published. A note like "1 case edited in the store since publish (kept)" would help.
> **Part 2, change the same case in the run:** Claude changed the title of TC-SCOREBOARD-001 in `testcases.json` (only that line) to "Score Board opened from the Login side navigation shows all challenges with the All category selected". Re-validation passed (47 cases, 0 findings) and the run was rendered again.
> ✅ **The review gate caught the change:** the dry run refused with "the test cases changed since they were reviewed. Review them again: qam review 20261030-1854-ChallengesWeb3." (exit 2). Nothing was written, and the ledger is unchanged.
> After I approved, `qam review` recorded the review. The dry run (`--refresh`) then showed:
> ```
> Conflict (1), not written
>   TC239 ← TC-SCOREBOARD-001  Test case 239 changed in the store since it was published (rev 1 → 2), so TC-SCOREBOARD-001 wasn't written. Review it there, or re-run with the store's version.
> Unchanged (46)
> ```
> It exited 1, and the ledger is unchanged. ✅ This is what the walkthrough expects. `--apply` was not run, because I said not to.
>
> **Was the conflict message clear?** ⚠️ Partly.
> - It names the case and the ADO revision change. It doesn't say **what** differs: the run changed the title, and ADO changed the steps. The tool works out the fields but doesn't print them.
> - "Re-run with the store's version" points at no command (the known gap). The only ways out are to edit the run by hand to match ADO, or to undo the ADO edit. Neither is described.
> - Here the two edits touch different fields (title in the run, steps in ADO), so they could be merged safely. The case is still held back as a whole.
