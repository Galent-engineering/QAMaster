# QAMaster 0.3.2: happy-path walkthrough on an application QAMaster has never seen

A full-loop walkthrough for any web application new to QAMaster. You need its source code and a way to run it locally.

The happy path:
1. Set up an empty QA project and map the app.
2. Write, review and publish test cases.
3. Change the app's code.
4. Let `/qamaster:check` pick the cases, draft their scripts, run them after your yes, and gate the push.

Each part says what's available now. The [limitations](#current-limitations) say what isn't yet (known) and what to watch for (unknown). [Goal insights](#goal-insights-and-future-goals) lists what to measure. Fill in each **Feedback** box as you go.

| | |
|---|---|

**Score each step:** ✅ worked · ⚠️ worked, but confusing or slow · ❌ broke or blocked me.

**Tip:** start requests with `/qamaster:…` or "QAMaster". The autonomous-qe plugin on your account can pick up similar wording first. If Claude reaches for `aqe`, note it and steer it back.

## Part 0. Prerequisites

QAMaster checks each of these and says how to fix it. Install only what you already know you need, and note whether QAMaster's messages were enough for the rest.

| For | What | QAMaster checks it in |
|---|---|---|
| Everything | Node.js 24 or later, npm, git 2.20+, `git config user.email` | `qam setup` (git, Node), `qam approve` (email), each gate command (git) |
| Running the app | Whatever its README needs (Docker, a database, seed data) | not QAMaster's |
| Mapping the app | Playwright and Chromium in the QA project; on Linux also `sudo npx playwright install-deps chromium` | `qam setup` installs them; `qam doctor` |
| Running drafted scripts | `npm install` in the automation folder (it downloads `@playwright/test` and `playwright-bdd`) | `qam check-scripts`; `qam doctor`, the `runner playwright-bdd` lines |
| The app's own pytest tests, if any | uv (or python3 with pytest), and `uv sync` in the test folder | `qam doctor`, `runner pytest`; the gate blocks with the command |
| The app answering | Running at its URL | `qam doctor`, `app URL`; a run that can't reach it is blocked, not failed |

> **Feedback, Part 0** (what you had to install; did QAMaster's message tell you how?)

## Part A. Set up and map the app

**Available now:**
- `qam setup`: config, Playwright, the code source, including a subfolder of a bigger repo.
- `qam doctor` and `/qamaster:status`.
- `/qamaster:dsm`: a scan of the code plus a safe crawl of the running app, which blocks writes after login.
- The `AUT-Skill-Builder` skill.

| Step | Do | Expected |
|---|---|---|
| A1. App | Clone the app fully and start it as its README says. Note its URL and a test account | The app opens and you can sign in |
| A2. Install | In the new QA folder: `git init`, `claude plugin marketplace add ~/claude-plugins/qamaster --scope project`, `claude plugin install qamaster@qamaster-local --scope project`, `claude plugin list` | qamaster 0.3.2, enabled, at project scope |
| A3. Setup | *"Set up QAMaster for `<App>`. It runs at `<URL>` and its front-end code is in `<folder>`."* For a monorepo, point at the front-end folder | The config is written with your app name. The source is recorded, as a subfolder if it is one. Playwright is installed |
| A4. Status | `/qamaster:status` | Each stage with its evidence, and the next step. It changes nothing |
| A5. Doctor | *"Run QAMaster doctor."* | Each line is ok or WARN, or says what to fix |
| A6. Sign-in | If the app has a login: create `.env.dsm` yourself with a test account. Claude never reads it | The crawl can sign in. `.env.dsm` stays git-ignored |
| A7. DSM | `/qamaster:dsm` | Routes from the router files, and screens from the crawl. **Write down:** the route count, screens, relations and elements, and anything missing (forms!) |
| A8. App knowledge | *"Build the AUT skills for this app."* | Skills under `.claude/skills/AUT_<App>*`, each citing the code |

> **Feedback, Part A** (counts; is any screen, form or route missing?)
>

## Part B. Test cases: generate, review, publish

**Available now:**
- TestGen at hallucination tolerance 0. The validator checks every screen, element, navigation and cited rule, flags credential-like text, and rejects a future `generated_at`.
- Review by your explicit yes.
- Publish with derived tags (`dir/*` for a shallow folder), smoke counted across the whole plan, and test data with a password masked in the store.

| Step | Do | Expected |
|---|---|---|
| B1. TestGen | *"Write test cases for the `<module>` module."* Start with a flow that works without signing in, then one with a form | Each run validates with 0 findings and 0 gaps, and is rendered. No password in a title or step |
| B2. Review | Read each run. Try *"show the dry run"* first, then answer **"Do you approve run X as reviewed?"** | "Show the dry run" doesn't count. Only your yes to the question records the review |
| B3. Publish dry run | `/qamaster:publish` (file store) | Creates, with `path:` tags under the front-end folder, and smoke "n of max 20 for the whole plan" |
| B4. Apply | Yes | `testcases/testcases.csv` is written. Commit the QA project |

> **Feedback, Part B** (are the cases right for this app? anything invented, missing or vague?)
>

## Part C. The automation folder

**Available now:** `qam app create` (a minimal web playwright-bdd template), `qam check-scripts` (layers, selectors, `@TC` tags and reuse; bddgen; `playwright test --list`).

| Step | Do | Expected |
|---|---|---|
| C1. Create | *"Create the automation folder."* | `<App>/` with `app.json` holding the app's URL |
| C2. Check | `qam check-scripts` before installing | **Blocked** (exit 2): "run npm install there" |
| C3. Install | `npm install` in `<App>/`, then commit | Script check: only "no feature files yet" |
| C4. Remote | Give the QA project a remote (a private repo, or `git init --bare ~/<app>-qa.git`) and push | Pushed |

## Part D. A code change, gated

**Available now:**
- The gate: `/qamaster:check`, with selection by `path:` tags, smoke, DSM impact (cases visiting the touched screens) and Claude's group picks.
- Just-in-time scripts: drafted for the selected cases, checked, recorded by hash, and approved together with the plan.
- The pytest and playwright-bdd runners, with one retry (failed then passed is flaky) and evidence: screenshot, video, trace.
- The push hook from Claude Code.

| Step | Do | Expected |
|---|---|---|
| D1. Gate the app repo | In the app clone: `.env` with `QAMASTER_TEST_ROOT=<QA project>` and `QAMASTER_STORE=file`, then *"Add the Claude Code entry point for QAMaster here."* | Recorded. `git status` in the clone shows neither `.env` nor `.qamaster/plans` |
| D2. A change | On a branch, change a front-end source file behind a module you published, and commit | A normal commit |
| D3. Push unchecked | *"Push this branch."* | **Blocked**: "Run /qamaster:check first" |
| D4. Check | `/qamaster:check` | A plan. Each case says why (covers / smoke set / visits / group). Manual cases are listed, and any coverage gaps. Then the automate step drafts scripts, checks them, records them, and asks **"Do you approve plan X?"** |
| D5. Look | Read the drafted scripts in `<App>/` | Selectors in `src/web/locators/`, credentials from environment variables. Cases that need an account or a CAPTCHA may stay manual, with the reason given |
| D6. Approve | Yes | They run. A new script's failure is labelled. An app that isn't up, or a missing browser, is **blocked** with the fix |
| D7. Push | *"Push this branch."* | Allowed after a pass |
| D8. Commit the scripts | In the QA project: review, commit and push them yourself | QAMaster never commits |
| D9. Publish the links | `/qamaster:publish`, then apply | `bdd:@TC-…` links, and `Script: <App>/features/… @ <commit>` |
| D10. Again | Another small change, then `/qamaster:check` | Scripts from the store's links run, kept. Nothing to draft |

> **Feedback, Part D** (were the picked cases the ones you'd pick? quality of the drafts, time, messages)

## Current limitations

### Known, and planned

| # | Limitation | What you may notice | Planned in |
|---|---|---|---|
| K1 | **Forms without a `<form>` tag are dropped from the DSM** (common in Angular and React) | Few form fields in the DSM, so form and boundary cases may be thin | Next patch ([plan 0.2.1 Later](../plans/0.2.1.md#later), item 1) |
| K2 | **Server routes are scanned only for some stacks** (ASP.NET MVC and Razor Pages, Spring MVC, Django, Flask; not Express, Laravel or Rails), and imports are followed in JS/TS only | The DSM covers the UI. API cases come only from TestGen's API channel. Fewer `path:` owners outside JS/TS | v2: API discovery; import following for C#, Java and Python |
| K3 | **A signed-in crawl needs your `.env.dsm`,** and the crawl blocks writes after login | Screens reached only after an action (an order placed, say) may be missing | By design (Q15). Crawl back-off on 503 is in Later |
| K4 | **Requirements fetch isn't built** | Stage 6 stays pending (optional) | After 0.3.0 (feature 6) |
| K5 | **Scripts are web only (playwright-bdd);** an existing framework isn't reused | No mobile, API or native scripts | v3: existing frameworks behind the Framework adapter (Q25) |
| K6 | **One selection preset (`standard`);** groups are Claude's `--tag` picks | No `fast` or `full` choice | Q31 presets, after the MVP |
| K7 | **Conflicts don't list the fields that differ, and there's no "take the store's version"**; an edit made only in the store isn't reported | Only if you edit cases in the store | Later ([plan 0.2.1](../plans/0.2.1.md#later)) |
| K8 | **The gate runs only from Claude Code** (the hook); there's no git pre-push hook and no PR checks | A push from a plain terminal isn't gated | v1.1 |
| K9 | **No reports, feedback or defect drafts** | Stage 15 stays pending | After 0.3.0 (Reports, Feedback) |
| K10 | **`/qamaster:status` lists automation stages 10–13 as pending,** though they're optional now that `/qamaster:check` drafts scripts (Q39) | Stages 10–13 pending | A small fix in the next patch |
| K11 | **Drafted scripts can race the page,** and sign-in scripts need credentials in environment variables | A "new script failed" label, or a flaky pass | Q39 labels it. Your review of the draft is the safeguard |
| K12 | **A file counts as shared only in plans of 20 or more cases** | With few cases published, a shared file still selects by path | By design (Q37 amendment) |

### Unknown: what to watch for

| # | Watch for | Why it might matter |
|---|---|---|
| U1 | **A monorepo, or the front end in a subfolder** | Do setup, `path:` tags and the gate's diff line up with the subfolder? |
| U2 | **Lazy-loaded or generated routes** | The route scan may find fewer screens |
| U3 | **Component-library controls** (dropdowns, date pickers, sliders, dialogs) | How TestGen names elements, and whether the drafted selectors hold |
| U4 | **Data left behind between runs** (carts, orders, registered users) | Flaky reruns. The app may need a reseed |
| U5 | **The front end and the API on different origins or ports** | The app-URL check, and the crawl's write blocking |
| U6 | **The app's size** | Plan time against the 30-second target, and drafting time |
| U7 | **Anything else new** | Write it down. That's what this walkthrough is for |

## Goal insights and future goals

**What this build should show on an unknown app:**
- The whole loop runs without hand-typed tags or links.
- Every selected or skipped case has a reason.
- The check is never green when a selected test failed or didn't run.
- Every setup problem names its fix.

**What comes next** ([releases.md](../releases.md), [product.md](../product.md#scope)):
- **Next patch:** K1 (forms) first, then K10, conflict polish (K7), and whatever this walkthrough finds.
- **v1.1:** a git pre-push hook and PR checks (GitHub Actions, Azure Pipelines) with a plan comment per PR, so the gate works outside Claude Code (K8).
- **v2:** MCP context sources (Jira, Confluence, Figma), importing existing test cases with gap analysis, locators from the crawl, API discovery (K2), and import following for C#, Java and Python.
- **v3:** existing automation frameworks (K5), impact and traceability matrices, root-cause evidence, value metrics, and a secrets vault.
